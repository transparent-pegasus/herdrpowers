# v1.3.0 — Independent test authoring, list roles, YAML as the single source of truth

## Summary

Three shipped defaults changed and one delegation task was added, all in service of the same property: **the pane that writes a test never wrote the code it covers, and the pane that reviews it is not alone in doing so.** A fourth change is editorial but load-bearing — prose no longer restates defaults, so `roles.yaml` is now the only place a route is stated.

## Default changes

| Task | v1.2.0 | v1.3.0 |
|---|---|---|
| `test-authoring` | coder / implementer | coder / **delegate** |
| `task-review` | **coder** / delegate | **reviewer** / delegate |
| `fix-round-re-review` | **coder** / delegate | **reviewer** / delegate |
| `documentation-impact-review` | planning-design / orchestrator | **generalist / delegate** |
| `fix-round-test-authoring` | — | coder / delegate (**new**) |

`plan-and-design`, `complex-coding`, `simple-coding`, `chores`, `review-fixes`, `verification`, `plan-double-review`, and `final-branch-review` are unchanged.

## A role that binds to a list runs one delegation per entry

v1.2.0 defined "one review per entry" inside the *Plan/design double review* section, which made double review a property of that one task. It is now a property of the **role**: any role declared with `agents:` (a list) instead of `agent:` runs one delegation per listed agent type, for any task assigned to it. The different-agent-types rule, the degrade-don't-block rule, and the name-it-in-the-report rule moved with it.

Because `task-review` and `fix-round-re-review` now resolve to the `reviewer` role, each per-task review and each fix-round re-review runs twice, in separate panes of different agent types. Findings merge into one list; a finding raised by either counts, and a finding is closed only when every re-reviewer that ran calls it ADDRESSED.

**This multiplies pane usage.** Worst case for one task with the shipped defaults: 1 implementer + 1 test author + 2 task reviewers + 5 rounds × (1 fixer + 1 fix-round test author + 2 re-reviewers). A repo that wants the old cost assigns those two review tasks to a single-agent role.

## Parallel test authoring

With `test-authoring: {mode: delegate}`, a task's tests come from a pane that is never shown the implementation:

- It gets its **own worktree detached at BASE** (`git worktree add --detach <plan-workspace>/tests-task-N BASE` — detached, because a named branch outlives `git worktree remove` and would collide with the next fix round, a parallel track at the same task number, and the next plan) — one writer per working tree still binds, and starting from BASE is where its RED comes from. The implementation genuinely does not exist there, so the new tests fail for the stated reason with no stashing or checkout games, and a test that *passes* there is a defect to investigate.
- It runs **in parallel with the implementer**, from the same brief. When both report, the test commit is cherry-picked into the task worktree and run: passing is the task's GREEN evidence, failing is a finding that enters the fix loop.
- **The brief must pin the interface.** Both panes work from the same text, so exact names, signatures, and values have to be in it. A task that genuinely cannot pin its interface up front delegates the test author *after* the implementer reports, handed the resulting interface and never the diff — same brief, same worktree-off-BASE, same RED, only the timing changes.

`fix-round-test-authoring` applies the same shape to a fix round, with one added constraint: its pane is neither the fixing pane nor the implementation round's test author. Tests for a fix written by whoever just changed the behavior prove only that the behavior changed.

`mode: implementer` remains available for both and restores v1.2.0 behavior task by task. Whichever runs, the report names the pane that wrote the tests — that requirement did not move.

## Where independence now comes from

v1.2.0's compensating control was "the reviewing pane audits test code the implementer wrote." That control is still the one that binds under `mode: implementer`, and it is no longer the only design on offer: under `mode: delegate` the tests are structurally independent of the implementation, and the reviews are structurally independent of each other. `docs/roles.md` states both, and what each costs.

## YAML as the single source of truth

Every `| Default |` column and every "with the shipped defaults that means…" sentence is gone from the payload and the docs. Prose now names what a task covers and says to read the resolved assignment; `commands/init.md` is instructed to read the shipped values out of `roles.yaml` rather than propose them from its own tables. A stale default in prose is worse than no default: it gives an agent a second, confident, wrong answer.

`CLAUDE.md` carries this as a maintainer invariant — a `| Default |` column in a payload table is now a bug.

## New file

- `skills/pane-driven-development/test-author-brief.md` — the delegation brief for `test-authoring` / `fix-round-test-authoring` in `mode: delegate`. Tests only, never production code, worktree deliberately behind, a passing test is a defect to report, RED evidence quoted, commit in its own worktree. Carries a fix-round variant: there the buggy implementation *is* present, and RED means the finding reproduces.

## Review round

An independent review of this change found eight issues, all fixed here. Five were consequences of adding a second writer pane to a loop built for one:

1. **One file, two contradictory contracts.** Both brief templates appended their contract to `task-N-brief.md`, which both panes read — so each was handed the other's instructions ("implement this" and "write tests only, never production code" in one file). The requirements file is now read-only for every pane, and each role's contract lives in its own file (`task-N-implementer.md`, `task-N-tests.md`, `task-N-fix-R-tests.md`) that names it.
2. **The merge step produced no evidence.** With the writers split, no single pane produces both RED and GREEN, and the review was still handed only the implementer's report — so a healthy task read as missing RED/GREEN. The orchestrator now runs the merged tests itself and appends a `Merged test run` section to the implementer's report; the reviewer gets the test author's report as a fourth path; `task-reviewer-brief.md` and `re-review-brief.md` know both shapes.
3. **The fix round could not satisfy its own evidence gate.** The fixer must show covering tests, but a separate pane wrote them afterwards and no step re-ran them. The fix round is now four ordered steps — delegate both, detached worktree at FIX_BASE, cherry-pick and run, consolidate — with the re-review delegated last. The shared test brief also claimed "the implementation does not exist," which is false in a fix round; hence the variant.
4. **Expected RED tripped the debugging gate.** Every workflow said "on any test failure, use `systematic-debugging`" while the test author is *required* to produce a failure. Verified-expected RED is now excluded; failures that survive the merge, or whose reason does not match the prediction, still trigger it.
5. **The test branch leaked.** `-b tests/task-N` is a fixed name and `git worktree remove` does not delete a branch, so the first fix round, a parallel track at the same task number, and the next plan would all collide. Test worktrees are now `--detach`.
6. **Pane accounting undercounted.** A track was budgeted one pane; with delegated test authoring it needs its whole writer set. `/execute_parallel` now counts the writer set per track and **waits** rather than computing a wave plan — degrading all the way to serial execution is a slow correct run, and the report says how much parallelism was achieved.
7. **`mode: orchestrator` was offered but unimplemented.** `init` let the user pick a third mode for both test-authoring tasks that no execution path handled. Removed from the template.
8. **The diff violated its own new rule.** Three workflow gate lines restated `generalist / delegate` in prose, and `init`'s validation step counted twelve delegation tasks when there are thirteen. Both fixed — the count now comes from `roles.yaml` rather than from a number written in prose, which is the same class of bug.

## Migration

A repo with an existing `.herdrpowers/config.yaml` keeps every value it wrote — the merge is per key, so nothing here changes an already-configured repo except `fix-round-test-authoring`, which is new and therefore falls through to this file's default. Re-run `/herdrpowers:init` to review the new task and the changed defaults together.
