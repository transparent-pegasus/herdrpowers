# v1.5.1 — delegation stays in the tab, `/full_cycle` runs tracks in parallel

## Summary

Two shipped defaults change, both configurable in the repository's `.herdrpowers/config.yaml` through a new `delegation:` block:

```yaml
delegation:
  pane_scope: tab       # tab | workspace | session
  execution: parallel   # parallel | serial
```

`roles.yaml` grows a third top-level block alongside `roles:`, `fallbacks:`, and `assignments:`, and it merges key by key like everything else.

## `pane_scope`: cross-tab delegation is off by default

Delegation previously selected from every pane `herdr pane list` returned. That list spans tabs, and a tab is how a herdr user separates projects — each pane reports its own `cwd`, and panes one tab over are routinely sitting in a different repository with their own user mid-task. Because `composer-submit.sh` **resets the target session**, a cross-tab delegation silently destroys that work and then points the agent at a worktree in a repo it has nothing to do with.

`delegation.pane_scope` now bounds candidacy before any role or assignment is consulted:

| value | eligible panes |
|---|---|
| `tab` | only panes whose `tab_id` equals the orchestrator's — the new default |
| `workspace` | any pane in the orchestrator's `workspace_id`, in any tab |
| `session` | every agent pane herdr reports — the pre-1.5.1 behavior |

The filter is a field comparison, not a heuristic: `herdr pane list` already returns `pane_id`, `tab_id`, `workspace_id`, `agent`, `agent_status`, and `cwd` per pane, and `using-herdr-sibling-panes` now carries the `jq` query that applies it.

Scope is a filter, not a preference. An out-of-scope pane is **not a candidate, not a last resort, not a fallback target, and not counted** when deciding whether an agent type is available. A type with no in-scope pane is *unavailable*, which is distinct from *exhausted* — it may have idle panes one tab over, and the fix is a configuration decision by the user, not a retry. Widening the scope mid-run is prohibited, under the existing rule that configuration is never written or reinterpreted from inside a run.

The cost is real and stated where the user chooses: a narrow scope leaves fewer panes for double reviews and parallel tracks. That is honest degradation, named in the report, not a silent loss.

## `execution`: `/full_cycle` parallelizes by default

`/full_cycle` Step 5 previously carried one conditional sentence — "when the plan has tasks that are genuinely independent … switch to `/execute_parallel`'s track extraction" — with no partition to act on and no point at which the question was forced. In practice runs serialized.

`delegation.execution` now names the strategy, defaulting to `parallel`:

- **`parallel`** — Step 5 takes the plan's `## Tracks` table, validates it against `/execute_parallel`'s Step 1 criteria, confirms it with the user, and runs the tracks through `/execute_parallel`'s Steps 2-3: one worktree per track off `<BASE_BRANCH>`, one implementation pane per worktree, integrated onto a coordination branch.
- **`serial`** — the plan's tasks run one at a time in a single worktree, as before.

It sets what is *attempted*, not what is forced: fewer than two independent tracks, or one usable pane, still runs serially. The report now names which strategy ran, how many tracks were confirmed, and how many actually ran concurrently — a `parallel` run that degraded to one track at a time is reported as degraded, not as parallel.

Two adjacent changes make Step 5 coherent:

- **Step 3 creates the coordination worktree** under `parallel`; per-track worktrees are created in Step 5 once the track table is confirmed. Step 7's verification runs in the coordination worktree holding the integrated result, never in a per-track one.
- **`delegation:` is resolved before Step 2**, not when Step 5 is reached, because the strategy shapes the plan and the worktree that precede it.

`/execute` and `/execute_parallel` are explicit user choices and ignore the key. `/strict_full_cycle` still overrides `enabled` and nothing else — it does not widen the scope to find a pane for a forced-on gate, and does not switch the strategy.

## Plans are written for track extraction

Parallel-by-default is worthless if the plan has no ownership boundaries in it. `writing-plans` gains an **Implementation Tracks** section and a `## Tracks` table in the plan header — each track's goal, tasks, owned file globs, and dependencies — plus a `**Track:**` tag on every task and a fourth self-review check (every task names a defined track; every file in a task's **Files** block falls under that track's globs).

The partition is drawn where the file structure is already in front of the author, instead of being re-derived afterwards from a document never written with ownership in mind. `/execute_parallel` Step 1 now validates a plan's existing table rather than deriving a second one that contradicts the tags on its tasks.

A single-track plan is an explicitly correct answer: one `main` track with one line saying why the work does not partition. Track grouping never overrides task right-sizing — tasks are sized first, then grouped.

## Migration

Both defaults change behavior for repositories that pin neither key.

- **`pane_scope`** — a repository that deliberately spreads one project across several tabs must set `delegation.pane_scope: workspace` (or `session`) in `.herdrpowers/config.yaml` to keep pre-1.5.1 reach. Everyone else gains the guard for free.
- **`execution`** — `/full_cycle` now attempts parallel implementation. Set `delegation.execution: serial` to keep the old sequential behavior. Plans written before this release have no `## Tracks` table; Step 5 derives a partition for them and says it did.

Re-running `/init` writes both keys explicitly, which is the recommended state — a key absent from the repo file follows `roles.yaml`, and `roles.yaml` moves across releases.
