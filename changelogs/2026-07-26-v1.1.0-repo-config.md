# v1.1.0 — Per-repo configuration: every assignment and every review gate

## Summary

`/herdrpowers:init` now writes a second deliverable, `.herdrpowers/config.yaml`, in the target repository. It holds the repo's **role assignments** and its **review gates** — every review in the pack is individually togglable there, and every role assignment overridable.

This fixes a real hole: role assignments previously lived only in `skills/orchestration/roles.yaml`, inside the pack. On plugin installations that file is read-only, so a user on Claude Code, Codex, or Cursor had *no way* to change who takes which task. On checked-in copies, editing it made the pack diff-dirty against upstream. There was no way at all to turn a review off short of editing pack files.

## Configuration resolution

Two files, merged **key by key**:

1. `<repo-root>/.herdrpowers/config.yaml` — the repository's own configuration. Wins.
2. `skills/orchestration/roles.yaml` — the pack's shipped defaults. Supplies every key the repo file omits.

Both carry the same schema, so there is no translation layer: `roles:`, `fallbacks:`, `reviews:`. An absent repo file means defaults throughout — existing repositories behave exactly as before this change.

`roles.yaml` gained a `reviews:` block (all five gates, `enabled: true`) so the default layer is complete, and a header comment stating it is the default layer and not the customization point.

## Review gates

Each entry under `reviews:` has exactly two knobs — `enabled` (does the gate run) and `role` (which role performs it):

| Gate | Runs in | Off means |
|---|---|---|
| `plan-double-review` | `/plan`, `/full_cycle` | Plans reach the user for approval unreviewed |
| `documentation-impact-review` | `/execute`, `/full_cycle`, `/quick` | No pre-implementation sweep for non-code files |
| `task-review` | `pane-driven-development` §3 | A task completes on the implementing pane's own report; no fix loop to enter |
| `fix-round-re-review` | the fix loop | Rounds close on the fix report's covering tests, command, and output; the five-round cap still counts them |
| `final-branch-review` | `/execute`, `/execute_parallel`, `/full_cycle`, `/quick` | The branch reaches the integration decision unreviewed |

The number of plan reviews is the length of `roles.reviewer.agents` — the assignment controls *who*, the gate controls *whether*. A one-entry list is a deliberate single review, not a degradation; an empty list is equivalent to disabling the gate. There is no redundant count key.

## What configuration cannot do

Three rules survive any config value, and each is stated at the point where an agent would be tempted to bend it:

- **A pane never reviews work it wrote.** Disabling a gate removes a review; it never converts one into a self-review.
- **The plan reviews that do run come from two different agent types.** A config that would put the same type in both Reviewer slots is overridden at runtime and the report says so.
- **Configuration is input, not state.** It is resolved once before the first delegation and never written from inside a run. Rewriting it mid-run to escape a stuck fix loop or route around an unavailable agent falsifies the terms the run reported under — `fallbacks:` and honest degradation exist for unavailability.

**Every disabled gate is named in the workflow's final report**, alongside any role that fell back and any review that degraded for lack of panes. A missing review is missing independence; the report says so every run, so an unreviewed branch is never mistaken for a reviewed one.

## Changes

### `commands/init.md`

- Two deliverables now, both committed: the `Herdrpowers Configuration` section and `.herdrpowers/config.yaml`. The config file is **tracked**, unlike `REPORT_DIRECTORY` and the sibling `.herdrpowers/pdd/` scratch workspace, which stay ignored.
- Step 1 reads `roles.yaml` for the defaults, loads any existing `.herdrpowers/config.yaml` as the base for an update run (never silently resetting a customization), and — inside herdr — runs `herdr pane list` so a default naming an agent type the user does not have gets flagged.
- New Step 3 proposes assignments and gates as one table of default-vs-proposed, and requires stating what each `enabled: false` costs *before* the user confirms it. Defaults are the proposal unless the repo or session gives a reason to differ.
- New Step 5 writes the annotated YAML template. Every key is written explicitly, including defaults: a key omitted from the repo file silently follows `roles.yaml`, which moves under the user on the next pack refresh.
- Validation now also checks the file parses, carries all four roles and all five gates, has no leftover angle-bracket placeholders, and is **not** git-ignored (`git check-ignore -v`).
- The report names every gate set to `false` and what independence it gives up.

### Consumers wired

- `skills/orchestration/SKILL.md` — new "Configuration resolution" and "Review gates" sections; the mid-run write prohibition; plan double review now keyed to the gate and to the resolved reviewer list. `fallbacks:` references now say "resolved", not "in `roles.yaml`".
- `skills/pane-driven-development/SKILL.md` — "Role Selection" became "Role Selection and Review Gates", resolving both once up front. §3 and the scoped re-review carry skip conditions; Final Review notes the caller's gate. Two new rationalization rows ("I'll turn the gate off to get past this loop", "task review is disabled, so the pane can review its own work") and two new Red Flags.
- `skills/requesting-code-review/SKILL.md` — names which gate it is and where it resolves from.
- `commands/plan.md`, `execute.md`, `execute_parallel.md`, `full_cycle.md`, `quick.md` — resolve the merged config before the first delegation; each gated phase opens with its `Gate:` line and skip behavior; each report requirement now names disabled gates separately from panes-unavailable degradation.
- `skills/using-herdr-sibling-panes/SKILL.md` — fallback resolution points at the merged map.

### Docs

- `docs/roles.md` — resolution order, the schema, the full gate table, and what configuration cannot do.
- `docs/workflows.md`, `docs/skills.md`, `skills/orchestration/README.md`, `README.md` — updated, with a short worked YAML example in the README's `/init` section.
- `docs/instruction_snippet.md` — target-repo rules mention the config file, the read-once rule, and the report duty.
- `CLAUDE.md` / `AGENTS.md` — "Roles, not tool names" became "Roles and gates, not tool names", naming `roles.yaml` as the default layer only and listing the four files a new role or gate must touch. Independence invariant now explicitly says no config value relaxes it.

## Naming

`.herdrpowers/config.yaml` — chosen over `orchestration.yaml` so the file can absorb future repo-level settings without a rename, and it sits beside the already-established `.herdrpowers/pdd/` workspace. The `pdd/` scratch directory ignores itself via its own `.gitignore`; the config file at the parent level is unaffected and stays tracked.
