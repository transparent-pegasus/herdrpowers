# v1.10.0 — `plan-double-review` becomes `plan-review`; availability is scope-aware; skill READMEs refreshed

## Summary

Three corrections, all of them places where the payload said something the pack's own invariants contradict.

The review gate was named `plan-double-review`, but the number of reviews comes from the reviewer role's `agents:` list, not from the task — a repo that binds `reviewer` to one agent type ran a single review under a task called "double". The task name now says what the task is (`plan-review`), and the count stays a property of the role.

The "Degrade, never block" rule counted an agent type as available if any pane of that type existed **in the session**, while "Delegation scope" three sections above says an out-of-scope pane is not a candidate and does not count toward availability. Under `pane_scope: tab` the two rules disagreed on the same question, so a run could wait for a busy pane in another tab it was never allowed to use.

Both skill READMEs described the pack as it stood several releases ago.

## What changed

### `plan-double-review` → `plan-review`

The `assignments:` key, its row in every gate table, and the prose that named it:

| File | Change |
|---|---|
| `skills/orchestration/roles.yaml` | the `assignments:` key |
| `skills/orchestration/SKILL.md` | gate table, development-cycle routing, the "Plan/design review" section heading and body |
| `commands/plan.md` | frontmatter description, the completeness sentence, Step 3's heading and gate, "wait for every review" instead of "wait for both" |
| `commands/full_cycle.md` | the gate line, the task list, Step 2's heading |
| `commands/quick.md`, `docs/development_cycle.md`, `docs/workflows.md`, `docs/roles.md`, `docs/skills.md` | the gate name and the task-level "double review" prose |
| `commands/init.md` | gate table row, config template key, a migration bullet |
| `.codex-plugin/plugin.json` | `longDescription` |

Prose that describes the **role** property — "a role bound to a list runs one delegation per entry, which is what makes a review a double review" — is unchanged in `CLAUDE.md`, `README.md`, `docs/roles.md`, `roles.yaml`, and `SKILL.md`. That statement was always about the role, and it stays.

`docs/development_cycle.md` Phase 2 also drops "Reviewer ×2": the count is whatever the resolved role binds.

### Stale `assignments:` keys are reported, not ignored

New rule in `skills/orchestration/SKILL.md` under "Configuration resolution": a key the shipped `roles.yaml` does not define is a stale name and is named in the final report, because the task it meant to configure is otherwise silently running on the shipped default. A repo config still carrying `plan-double-review` is honored as `plan-review`, with the rename reported.

Without this, a repository that had deliberately set `plan-double-review.enabled: false` would silently get the gate back on the first run after upgrading — a disabled review re-enabling itself is exactly what the reporting invariant exists to prevent.

### Availability is scope-aware

`skills/orchestration/SKILL.md`, "Roles that bind to a list": an agent type counts as available if any **in-scope** pane of that type exists, not any pane in the session. This aligns the rule with "Delegation scope" and with the `delegation.pane_scope` invariant in `CLAUDE.md`.

### Skill READMEs

`skills/orchestration/README.md` no longer hard-codes routing in prose ("delegates complex coding … to Coder agents, and everything else to Generalist agents") — a `| Default |` in prose form, wrong since v1.8.0 moved the Generalist onto the orchestrator. It now points at the routing table and covers `delegation:`, list roles, `mode: orchestrator` reviews, and the reporting rule.

`skills/using-herdr-sibling-panes/README.md` gained what the skill has accumulated since it was last touched: `delegation.pane_scope`, the composer width floor, the shell-prompt and bare-`/word` refusals, report files, the `git checkout`/`restore`/`stash`/`clean`/`reset` prohibition, report-file polling on long work, the `[Pasted Content …]` non-submission, and the fact that helper exits `2`/`4` and a policy refusal never count toward exhaustion.

## Migration

A repository whose `.herdrpowers/config.yaml` sets `plan-double-review` should rename that key to `plan-review`. Until it does, orchestration honors the old key and says so in the report; re-running `/herdrpowers:init` rewrites the file with the current names.

No other key, role, mode, or invariant changed.
