# v1.4.0 — `/strict_full_cycle`, and `/quick` gets an isolated workspace

## Summary

Two workflow changes, no default changes. A new workflow runs the full cycle with every review gate forced on, and `/quick` stops working in the primary checkout.

## New workflow: `/strict_full_cycle`

`commands/strict_full_cycle.md` is a delta over `/full_cycle`, not a copy of it: it instructs the agent to read and follow `full_cycle.md` end to end, then states one override. Duplicating a 100-line workflow to change one key would have produced two files drifting apart on every later edit.

The override: **`enabled` is ignored on every review task in the resolved configuration.** `plan-double-review`, `documentation-impact-review`, `task-review`, `fix-round-re-review`, `final-branch-review`, and any review task a later release adds all count as `enabled: true` for that run, so `/full_cycle`'s "when it is disabled, skip" clauses never fire.

What the override deliberately does not touch:

- `role`, `mode`, `roles:`, and `fallbacks:` still bind exactly as resolved. Strict mode changes one key, not the routing.
- The invariants are untouched — a pane still never reviews work it wrote, and a review whose role binds to a list still runs once per entry.
- The configuration file is never written. `enabled: false` stays where the user put it; the run declines to honor it for that run only, which keeps `orchestration`'s "never write either file from inside an orchestrated run" intact.
- A forced-on gate that has no available pane degrades per `orchestration`'s existing rules. Forcing a gate on is a decision, not a guarantee that the review happened.

Reporting is the other half: the final report gains a **Review gates forced on by strict mode** section naming each gate whose resolved `enabled` was `false`, or states plainly that nothing was disabled and the run was identical to `/full_cycle`. Same principle as the existing rule that a disabled review is named — a reader must never have to guess which gates ran.

`skills/orchestration/SKILL.md` and `docs/roles.md` now say, next to the review-task table, that `/strict_full_cycle` ignores that column. Without it the skill and the workflow would contradict each other on the one key the workflow overrides, and an agent reading only the skill would resolve it the wrong way.

## `/quick` runs in a worktree

`/quick` previously omitted workspace isolation, which put small changes directly in the primary checkout on whatever branch was current. It now runs `using-git-worktrees` as Step 2, off `<BASE_BRANCH>`, and the phases renumber to 8.

Consequences that came with it, all in `commands/quick.md`:

- **Delegations carry the worktree path.** The Orchestration section gained `/full_cycle`'s delegation-contract paragraph; without it a delegated pane would work in the wrong tree.
- **The delegated test author no longer improvises.** With no branch isolation, `mode: delegate` had to describe a throwaway worktree at "the pre-change commit". It is now the same shape `pane-driven-development` uses: record BASE in the worktree, `git worktree add --detach` at it (still never `-b`), cherry-pick back, orchestrator runs the merged tests for GREEN.
- **Verification runs in the worktree**, not in the primary checkout.
- **The branch is handed back.** A workflow that creates a branch and never offers it back leaves the work invisible in the user's checkout, so Step 8 presents `finishing-a-development-branch`'s candidates — merge locally, push and open a PR, push only, or keep — and executes only the chosen one. This is the pack's "integration is offered, not assumed" guarantee, which `/quick` previously escaped by not producing a branch at all.
- The "small enough to proceed without an isolated worktree" execution requirement is gone; the remaining bar is the absence of a written plan.

`/quick` is now `/full_cycle` minus the written plan and its double review. That is the honest description, and `docs/workflows.md` says so.

## Files changed

`commands/strict_full_cycle.md` (new), `commands/quick.md`, `commands/init.md`, `skills/orchestration/SKILL.md`, `docs/workflows.md`, `docs/roles.md`, `docs/development_cycle.md`, `docs/instruction_snippet.md`, `README.md`, and the four plugin manifests.

## Migration

Nothing to do. No shipped default moved, so `.herdrpowers/config.yaml` in any repository keeps its meaning exactly. `/strict_full_cycle` is opt-in per run; `/quick` behaves differently only in that it now branches and isolates before implementing, which requires `<BASE_BRANCH>` to be declared in the repository's `Herdrpowers Configuration` section — it already was, for every other workflow.
