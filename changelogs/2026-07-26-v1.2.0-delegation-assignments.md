# v1.2.0 — Every delegation is a configurable task assignment

## Summary

v1.1.0 made the five **reviews** togglable and the role→agent bindings overridable, but left the routing of everything else hard-coded: implementation always went to Coder, chores always to Generalist. This release finishes the job. The config is now a **role list** plus a **role assigned to every delegation task** — review, implementation, tests, chores, verification, plan/design, fixes. No skill or command hard-codes a route any more.

## Schema change: `reviews:` → `assignments:`

v1.1.0's separate `reviews:` block is gone; work tasks and review tasks live in one table, because they are the same thing — a unit of work handed to a role. Nothing shipped on the old schema for long enough to need a migration path, so this is a straight replacement rather than a deprecation.

```yaml
roles:                                  # ← the role list
  planning-design: { agent: orchestrator }
  reviewer:        { agents: [codex, cursor] }
  coder:           { agent: codex }
  generalist:      { agent: cursor }

fallbacks:
  cursor: [grok]

assignments:                            # ← a role per delegation task
  complex-coding:      { role: coder,      mode: delegate }
  chores:              { role: generalist, mode: delegate }
  test-authoring:      { role: coder,      mode: implementer }
  task-review:         { role: coder,      mode: delegate, enabled: true }
  …
```

Resolution is unchanged: `<repo-root>/.herdrpowers/config.yaml` over `skills/orchestration/roles.yaml`, merged key by key, absent repo file meaning defaults throughout.

## The twelve delegation tasks

Every task takes `role` (from the role list) and `mode`:

- `delegate` — a fresh idle pane of that role, through `using-herdr-sibling-panes`
- `orchestrator` — the orchestrator pane itself; nothing delegated
- `implementer` — the pane that already owns the task does it

**Work tasks** (mandatory; `mode` decides whether they are delegated):

| Task | Default | Covers |
|---|---|---|
| `plan-and-design` | planning-design / orchestrator | Brainstorming, design docs, implementation plans |
| `complex-coding` | coder / delegate | Implementation over the complex-coding boundary |
| `simple-coding` | generalist / delegate | Localized, pattern-following edits under it |
| `chores` | generalist / delegate | Lookups, file moves, log gathering, mechanical edits, lint/format |
| `test-authoring` | coder / implementer | Writing a task's tests |
| `review-fixes` | coder / implementer | Fixing review findings |
| `verification` | generalist / delegate | Baseline and supplemental verification commands |

**Review tasks** (same knobs plus `enabled`): `plan-double-review`, `documentation-impact-review`, `task-review`, `fix-round-re-review`, `final-branch-review`.

`enabled: false` is only for reviews. A work task is never disabled — `mode: orchestrator` is how one stops being delegated, and init's validation rejects `enabled: false` on a work task rather than silently accepting a knob that means nothing.

A repo may also **define a role beyond the shipped four** and assign tasks to it; init says so and validates that every assignment names a role `roles:` defines.

## What no assignment can change

Three hard rules, restated at every point an agent would be tempted to bend them:

- **A pane never reviews work it wrote.** A config that routes a review to the implementing pane is overridden at runtime and the report says so. Disabling a review removes it; it never converts one into a self-review.
- **The plan reviews that do run come from two different agent types.**
- **`review-fixes` escalates at fix-loop rounds 4-5** to a fresh pane of an escalated agent type, whatever its mode says.

## The one deliberate loosening: `test-authoring`

The pack's independence invariant has two halves: the reviewer never reviews its own code, and — because the implementing pane writes its own tests — the reviewer **audits the test code** as the compensating control for having cut the old `test-engineer` role (see v1.0.0's reconciliation notes).

Making `test-authoring` assignable means a repo can set `mode: delegate` and split those halves. That is now allowed, with the cost stated wherever the choice appears: init says it before the user confirms, `orchestration` and `pane-driven-development` say it at the routing point, and the workflow's report must **name which pane wrote the tests** so the missing pairing is visible. `CLAUDE.md`'s invariant was updated to describe the test half as reassignable-but-reported rather than fixed — the review half stays absolute.

## Changes

### `skills/orchestration/roles.yaml`

Restructured into three commented blocks: the role list, `fallbacks:`, and `assignments:` with all twelve tasks. Each task carries a `description` so the default file reads as the reference copy.

### `skills/orchestration/SKILL.md`

- "Review gates" became "Delegation tasks and their assignments": the knobs, both task tables, and a "What no assignment can change" subsection.
- **"Task routing" is now two steps** — name the task, then read its assignment — replacing the old three-way prose rule. Explicit instruction not to substitute judgment for a configured route.
- **"Development-cycle routing" no longer holds a second, hard-coded mapping.** It states what the *defaults* produce and points at the table.
- **"Complex coding boundary" now decides a task name**, `complex-coding` vs `simple-coding`, not a role. A repo that assigns both to one role makes the distinction moot — called out as legitimate.
- Frontmatter description rewritten.

### `skills/pane-driven-development/SKILL.md`

- "Role Selection and Review Gates" became "Delegation Assignments", with a table of the six tasks that drive the loop and where each lands.
- Third loop-shape change documented: `test-authoring: {mode: delegate}` strips RED-GREEN-REFACTOR ownership from the implementer's brief and requires the report to name the test author.
- "Delegation Model (READ FIRST)" bullet 2 rewritten from an absolute to a default plus its cost.
- Internal cross-references updated to the new section name.

### Commands

`plan.md`, `execute.md`, `execute_parallel.md`, `full_cycle.md`, `quick.md`: the hard-coded "Implementation → Coder panes / Chores → Generalist panes" bullet lists are replaced by "Routing comes from `assignments:`, not from this file", followed by what the shipped defaults produce and an instruction not to assume them. Gate lines renamed to `assignments.<task>`. The TDD rule requirement now names the `test-authoring` assignment and its `delegate` branch. Report duties now cover non-default assignments and modes, not just disabled reviews.

### `commands/init.md`

Split into two proposal steps, matching the two lists:

- **Step 3 — Propose the Role List.** Each role, what it binds to, what it means. Notes that a repo may add a role.
- **Step 4 — Assign a Role to Each Delegation Task.** Both task tables with defaults, plus the rules to state while proposing: what each `enabled: false` costs, that work tasks use `mode: orchestrator` rather than being disabled, what `test-authoring: delegate` gives up, the two non-configurable invariants, and that `review-fixes` escalates regardless.

The template now writes `roles:` / `fallbacks:` / `assignments:` with all twelve tasks. Validation checks every task is present with a `role` that exists in `roles:` and a valid `mode`, that only the five reviews carry `enabled`, and that no work task carries `enabled: false`.

### Docs

`docs/roles.md` gained a "Delegation Tasks" section with both tables and the invariants; its Coder section and `README.md`'s TDD principle are now phrased as defaults rather than absolutes. `docs/workflows.md`, `docs/skills.md`, `docs/instruction_snippet.md`, `skills/orchestration/README.md`, and `README.md` (worked example rewritten to show `roles:` + `assignments:`) updated. `CLAUDE.md` / `AGENTS.md`: the invariant is now "Roles and task names, not tool names", with "no skill or command may hard-code a route" and the four files a new role or task must touch.
