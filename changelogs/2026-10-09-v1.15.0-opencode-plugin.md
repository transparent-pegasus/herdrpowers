# v1.15.0 — OpenCode plugin

## Summary

OpenCode becomes a supported harness, installed like the
`artful-simplicity` plugin:

```bash
opencode plugin -g herdrpowers@git+https://github.com/transparent-pegasus/herdrpowers.git
```

OpenCode installs plugins as npm packages and loads `package.json`'s `main`.
The new root `package.json` points `main` at `.opencode-plugin/index.mjs`,
whose `config` hook appends the bundled `skills/` to `skills.paths` and
registers every `commands/*.md` as an OpenCode command. It ships in 1.15.0
together with the upstream v6.4.2 refresh; neither was released alone.

## Details

- **Same structure as `artful-simplicity`:** a `.opencode-plugin/` entry
  point beside the other harness directories, plus a root `package.json`
  mirroring the plugin manifest's fields. Two adaptations follow from this
  payload.
- **Commands are registered too.** `artful-simplicity` ships skills only;
  this pack's Codex and Cursor manifests both expose `commands/`, and OpenCode
  has no command directory a plugin can point at — only `config.command`, keyed
  by name. The hook reads each file's `description:` frontmatter and uses the
  rest as the template. The commands carry no `$ARGUMENTS` or `$N`
  placeholders, so OpenCode appends whatever the user types after the command.
- **Commands are namespaced `/herdrpowers:<name>`.** OpenCode applies config
  commands after its built-ins, so a plain `init` would silently replace
  OpenCode's own `/init` (AGENTS.md setup). The prefix avoids that and matches
  the names Claude Code gives the same commands, so the docs'
  `/herdrpowers:init` works on both. An existing command of the same name in
  the user's configuration wins (`??=`).
- **`index.mjs`, and no `"type": "module"`.** `artful-simplicity` declares
  `"type": "module"` in `package.json`. Here that would make Node load
  `skills/writing-skills/render-graphs.js`, a CommonJS script, as an ES module
  and fail on its first `require`. Verified both ways before choosing the
  `.mjs` extension. `CLAUDE.md` now says so, and records that `package.json`
  carries the pack version alongside the four manifests.
- **No bootstrap injection.** Upstream's OpenCode plugin injects its
  meta-skill into every session; this pack has no session-start hook on any
  harness, and its entry skill (`orchestration`) triggers from its
  description like every other skill. OpenCode also exposes each skill as a
  slash command of its own.
- `README.md` gains the install line, a Supported Platforms row, and the two
  new paths in Repository Structure; `docs/skills.md` and `docs/workflows.md`
  name OpenCode; `AGENTS.md` lists the new entry point (and now counts 7
  workflows, not 6).
- `CLAUDE.md`'s validation list gains a Node one-liner that runs the config
  hook and prints the skills path and the registered commands.

## Verification

Against OpenCode 1.18.35, with isolated XDG config, cache, data, and state
directories so no user configuration was read or written:

- `opencode debug config` with the plugin loaded by file URL, and again as
  the package spec `herdrpowers@file:<repo>` (which resolves `main`): the
  `skills/` path and all seven `herdrpowers:*` commands, each with its
  description.
- `opencode debug skill`: all 16 skills discovered from `skills/`.
- `GET /command` on `opencode serve`: the seven `herdrpowers:*` commands
  alongside the untouched built-in `init` and `review`.
- `node skills/writing-skills/render-graphs.js` still renders with the new
  `package.json` in place; `claude plugin validate` passes for the plugin and
  the marketplace.

## Not changed

- No skill or command file changed: the plugin reads them as they are.
- Using an OpenCode pane as a delegation *target* is a separate question —
  `composer-submit.sh` is verified only against codex, cursor-agent, and grok.
  Run `probe-composer.sh` against an OpenCode pane before routing work to it.
- `roles.yaml`, routing, and review gates untouched.
